# Validation reports: every count is backed by a committed JSON

Each success count quoted in the README/METHOD is backed by a machine-readable
report in `results/`, generated by:

```bash
uv run python scripts/gen_validation_reports.py
```

All legs run the closed loop on the verified nominal
`results/nom_n5_gluck_cont.npz` in the force-saturated simulator
(`rollout_zoh`, hard `np.clip`, RK4 sub-stepping) at the **60 N** bound, judging
each perturbed-IC rollout against the committed success predicate (`v1`). The
actuator force is clipped to the bound by construction, so "force within bound" is
trivially true and gates nothing; the meaningful gates are the track limit and the
continuous 5 s hold, and the actuator is allowed to ride saturation (disclosed per
leg via `n_saturated_ics` and `max_abs_force_demanded`).

The verification boundary (what "validated" means, predicate `v1`, empirical not
formal, sim not hardware) is defined once in the README verification-boundary box.
This file backs each count with a committed JSON.

## Validation legs

All on `nom_n5_gluck_cont.npz`, F = 60 N, predicate `v1`, ρ = 0.0297679. ρ is
computed once from the nominal linearization (force- and IC-independent), so the
identical ρ in each per-leg JSON is one number, not a per-leg re-verification.

These are two distinct claims at two distinct perturbation amplitudes: **88/88 at
σ=0.02** (24 banked A + 40 banked B + 24 fresh) and **24/24 at σ=0.10** (5× stress).
The two legs have no single pooled success rate, so they are never merged into one
number. Banked (two-seed, σ=0.02) total: **64/64**. Every leg matched its previously
quoted count exactly. The `peak |u| applied` column is the clipped force the plant
actually saw; `raw demand` is the pre-clip force the controller asked for
(`max_abs_force_demanded`); `sat. ICs` is `n_saturated_ics`, the number of ICs in
the leg whose raw demand hit the 60 N bound on any tick. Only the 5× stress leg
rides the saturation (11 of 24 ICs); the default-σ legs never reach the bound.

The nominal swing-up horizon is **6.0 s** (`nominal_horizon_s`); the closed-loop
rollout that each IC is judged over is longer, **12.0 s** (`rollout_duration_s` =
6.0 s swing-up + 5 s hold + a 1 s settle budget). The 5 s continuous-hold
predicate is evaluated over the tail of that 12 s rollout.

## Cart excursion over the whole rollout

The `max_abs_x` column is the peak cart displacement over the **whole** rollout,
including the swing-up before the hold window (the predicate caps `|x| ≤ 2 m` only
during the final 5 s hold). The worst peak across all legs is **4.075 m** (the 5× stress leg); the n=5
nominal itself peaks at **3.69 m** (range 3.71 m). All sit well inside the ±10 m
rail. README "Cart excursion" covers the hardware-rail implication.

## Each report contains

`commit_sha`, `python_version`, `nominal` path + `nominal_sha256`, `seed`,
`sigma`, `n_trials`, `n_success`, `frac` + Wilson CI, `force_limit`,
`max_abs_force` (clipped force applied), `max_abs_force_demanded` (raw pre-clip
demand), `n_saturated_ics` (ICs that hit the bound), `max_abs_x` (peak cart
excursion over the whole rollout), `nominal_horizon_s` (6.0 s swing-up) and
`rollout_duration_s` (12.0 s judged rollout), `monodromy_rho`, and the full
`predicate` block (version `v1` + thresholds, with `xdot_tol_m_s` in m/s).
