# Validation reports: every count is backed by a committed JSON

Each success count quoted in the README and METHOD is backed by a machine-readable
report in `results/`, generated by:

```bash
uv run python scripts/gen_validation_reports.py
```

All legs run the closed loop on the validated n=6 nominal selected in
[`configs/nominal.py`](../configs/nominal.py) (the native 1 ms-grid
`results/nom_n6_gluck_cont.npz`) in the force-saturated simulator (`rollout_zoh`,
hard `np.clip`, RK4 sub-stepping) at the 60 N bound, judging each perturbed-IC
rollout against the committed success predicate `v1`. The actuator force is clipped
to the bound by construction, so "force within bound" is trivially true and gates
nothing; the meaningful gates are the track limit and the continuous 5 s hold. The
actuator is allowed to ride saturation, disclosed per leg via `n_saturated_ics` and
`max_abs_force_demanded`.

The verification boundary (what "validated" means, predicate `v1`, empirical not
formal, sim not hardware) is defined once in the README verification-boundary box.
Each per-leg JSON also records `nominal_grid_ms` (1.0) and `nominal_native_1ms`
(`true`), so the native 1 ms rigor status travels with every count. These JSONs
were generated against the 1 ms nominal.

Banked two-seed total: **48/48**. Peak cart force over all validation runs is
≤ 38.6 N of the 60 N bound. The raw pre-clip demanded force is also ≤ 38.6 N and
`n_saturated_ics` is 0 across both legs, so zero ticks were clipped in any run.
Monodromy ρ ≈ 0.0270 (≪ 1, strongly contracting); ρ is computed once from the
nominal linearization (force- and IC-independent), so the identical ρ in each
per-leg JSON is one number, not a per-leg re-verification. Each committed report
records
its `nominal_sha256`, `nominal_grid_ms` (1.0), `nominal_native_1ms` (`true`),
per-leg `max_abs_force`, `max_abs_force_demanded`, `n_saturated_ics`, and
`max_abs_x`, and the full predicate block.

## Cart excursion

`max_abs_x` is the peak cart displacement over the whole rollout, including the
swing-up phase before the hold window. The predicate caps `|x| ≤ 2 m` only during the final 5 s hold; during
swing-up the cart travels further. The n=6 nominal itself peaks at 4.582 m (range
4.625 m), larger than n=5 (3.69 m). All sit well inside the ±10 m rail bound, but a
real n=6 rig would need about 5 m of usable travel, or a re-solve under a tighter
track constraint. The README "Cart excursion" point covers the hardware-rail
implication.

## Each report contains

`commit_sha`, `python_version`, `nominal` path + `nominal_sha256`,
`nominal_grid_ms`, `nominal_native_1ms`, `seed`, `sigma`, `n_trials`,
`n_success`, `frac` + Wilson CI, `force_limit`, `max_abs_force`,
`max_abs_force_demanded` (raw pre-clip demand), `n_saturated_ics` (ICs that hit
the bound), `max_abs_x` (peak cart excursion over the whole rollout),
`nominal_horizon_s`, `rollout_duration_s`, `monodromy_rho`, and the full
`predicate` block (version `v1` + thresholds).
